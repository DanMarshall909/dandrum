## Safety, architecture, and alternatives

Read the pinned GTK 0.18.2 `WidgetExtManual::destroy` contract: no subsequent widget-state query. Current source obtains the display first and only calls sync on that previously retained display afterward; dropping the inert GTK wrapper only unrefs. The private owner exposes neither container nor WebView handles through public APIs, has no Clone, and GTK-bearing fields enforce the safe thread-affinity boundary. Public creation validates the initialized GTK thread. Host-parent XID is borrowed; neither host parent, shared GDK display, nor X server is disposed. This is UI-edge work, not audio callback work.

NativeEditor disconnects and unregisters its IPC handler before its fields drop in declaration order: Wry WebView, then OwnedWindow. Pinned Wry's GTK InnerWebView Drop destroys its WebKit widget. The outer container is separately edge-owned. On checked reparent error the owner unwinds before acquisition-local native/Fixed wrappers; those wrappers only unref afterward and are not queried. On builder preflight error local temporaries unwind safely. The observing resource handler collects integer XIDs while the container is live; temporary GTK aliases do not escape. Existing production/navigation strong WebView aliases are explicitly dropped before owner disposal. Weak-notify handles/counters do not retain live-use widget aliases.

This is one audited unsafe operation under deny, with no broad module allow. Explicit forbid continues on assets and native tests and on configurations outside Linux/native-X11. Clippy with warnings denied verifies the expectation is fulfilled in the final native build. No GUI types or unsafe code migrate into the format-neutral host or engine. No dependency, generated bundle, CMake, resource policy, public transport, or security capability changes. Existing local-origin/CSP behavior remains independently exercised.

A materially simpler safe alternative was considered against the pinned implementation. Safe close queues an idle delete request and may be inhibited; display sync cannot dispatch that future GTK work. Dropping a Rust GtkWindow wrapper alone leaves GTK's internal toplevel reference (confirmed in installed Gtk GIR). Safe unrealize/hide can affect native visibility but does not discharge complete container/callback ownership. Pumping GTK inside Drop would dispatch reentrant host work; waiting afterward changes the contract. Generic GObject run_dispose is itself unsafe and less intent-specific. Raw XDestroyWindow bypasses GTK ownership; changing backend or lifecycle API expands scope. The chosen narrow widget destroy plus display barrier is therefore the smallest appropriate disposal operation, with its safety obligations visible.

The prior readiness record is accurately historical. Independently verified its 16 non-current source/library/log bindings; its three prior runtime hashes are not falsely applied to this candidate. Installed GTK/GDK, pinned binding/Wry code and GIR agree with the queued-close versus disposal distinction. The original unidentified-child failure still has unknown identity/cause. This new exact-XID RED establishes the present contract defect independently; successful retries do not retrospectively diagnose that earlier failure.
