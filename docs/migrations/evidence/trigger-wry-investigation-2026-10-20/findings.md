# Wry/X11 investigation, 20 October 2026

Decision: adopt pinned Wry 0.57.0 for the next task-3.2 implementation fixture. Keep production integration deferred. The bounded question was whether the selected library can create, service and destroy a local-content child under an external X11 parent without starting its own event loop. The investigation budget was 20 minutes; success required a compiled pinned fixture and two independently queried parent/child lifecycles. Failure would defer Wry adoption and retain the headless product.

The isolated fixture passed two cycles on `DISPLAY=:10.0` with `GDK_BACKEND=x11`. Each created an Xlib host parent, loaded HTML through `dandrum://localhost/index.html`, observed its literal `local-ready` IPC message, queried exactly one direct X11 child, asserted unmapped/mapped states after hide/show and proved that dropping the WebView removes the child while the host parent survives. The fixture calls bounded nonblocking GTK iterations as a synthetic host tick. It starts no GTK main loop. This is a library feasibility probe, not proof that a real CLAP host services GTK correctly. The EGL warning is retained in the successful raw run.

## Lifecycle findings for the implementation

- Wry's `WebView` is neither `Send` nor `Sync`; own it only in the plugin's main-thread GUI state. Rust's `Send` trait permits ownership transfer between threads; its absence here makes that transfer a compile-time error. Preserve an explicit creation-thread check for adapter entrypoints too.
- Initialize GTK on that thread before `build_as_child`. Select X11 explicitly and reject a non-X11 GDK display before Wry downcasts it. Accept a validated Xlib parent; Wry 0.57.0's Linux path rejects other raw handle variants.
- Clack at pinned revision `27ca28391b57a61bad4bb5099288a7bf9247350d` includes host/plugin timer support. The next fixture should register a host timer and perform a bounded number of nonblocking GLib/GTK iterations per callback, unregistering before destruction. Timer refusal and missing support need explicit results. The probe does not establish the actual CLAP timer contract.
- Use `build_as_child`, never `build` on a foreign host window. The child path creates a separate X11 container; the library's teardown destroys that container. Passing the host window through the ordinary build path risks giving that teardown the host's window identity.
- Exercise injected failure after native container creation. Source review shows X11 ownership is attached after `new_gtk` succeeds; the error path needs an actual resource-count oracle before claiming cleanup. This is an investigation finding, not a reproduced leak.
- Close admission, invalidate callback generations, unregister host callbacks, release view-owned activity and then drop the WebView on its creation thread. Reopen with a fresh attachment. The probe verifies native child destruction, but does not prove callback cancellation, held-note cleanup or session recovery.
- Avoid Wry's synchronous cookie methods: their Linux implementation runs nested GTK iteration loops. The selected local editor needs no cookie API. Custom protocol handlers and IPC support the needed resource/transport boundary.

## Dependency and licensing scope

The fixture pins Wry `=0.57.0`, GTK `=0.18.2`, x11-dl `=2.21.0` and raw-window-handle `=0.6.2`; its lockfile records transitive resolutions. Wry defaults enable `os-webview` and `x11`. Linux WebKitGTK bindings remain pinned by Wry to `=2.0.2`, JavaScriptCore bindings to `=1.1.2`; system development packages were already installed. Wry declares MIT OR Apache-2.0. `linux-license-declarations.json` records Cargo declarations for the resolved Linux graph, including build dependencies. Those declarations do not settle system-library redistribution notices or installed packaging obligations. The all-platform metadata query lacked cached packages; the retained declaration list intentionally uses `--filter-platform x86_64-unknown-linux-gnu`.

No Wry dependency, GTK type or native handle has been added to the format-neutral host or production CLAP crate. Next task 3.2 still owns production bundle/fonts, local-only navigation/resource policy, fixed dimensions, invalid parent/order/API failure cleanup and actual host-driven servicing. Later 3.3 and 4.2 own protocol/session and real CLAP integration.
