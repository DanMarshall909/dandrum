# Drum voice authoring (808/909-style)

This document backs the `add-drum-voice-authoring` change. It records the
primitive inventory used to build the initial 808/909-style drum library, the
primitive improvements made along the way, the reference-seeded parameter
defaults and their provenance, the no-proprietary-content policy, and the
offline spectral/envelope tuning plan.

The guiding principle is **primitives first, bespoke modules last**: every drum
voice is an ordinary Dandrum instrument graph composed from reusable DSP
primitives, and public controls are declared through `preset_surface.parameters`.
No machine-specific `808_kick`/`909_snare` module type was introduced.

## 1. Primitive inventory (task 1.1)

The graph model already exposes the primitives a drum voice needs. The initial
library is built from this set alone:

| Primitive        | Role in drum voices                                             |
| ---------------- | -------------------------------------------------------------- |
| `oscillator`     | Tuned body tone; waveform (sine/triangle/saw/square) selectable |
| `noise`          | Snare/clap/hat noise source (global-scoped, always running)     |
| `decay`          | One-shot exponential/linear envelopes for amp, pitch, transient |
| `adsr`           | Gated envelope where sustain/release matter                     |
| `filter`         | Highpass/lowpass/peaking shaping of body and noise (biquad/moog) |
| `impulse`        | Click/transient excitation                                      |
| `gain`           | Per-voice VCA and static level trims                            |
| `curve_mapper`   | Pitch-sweep shaping and constant/scaled control values          |
| `note_to_control`| Note → pitch ratio / gate / velocity                            |
| `audio_mixer`    | Final voice summing bus (global scope)                          |
| `sampler`        | Fallback source for metallic 909 voices (see §3)                |

### Voices buildable without new DSP modules

All synthesized voices in the initial library are pure primitive graphs:

- **808:** kick (`examples/patches/synthetic-808-kick.yaml`), snare, tom, conga,
  clap, cowbell.
- **909:** kick, snare, tom, clap.

Only the **909 hats, crash, and ride** use the `sampler` primitive (see §3).

## 2. Primitive improvements made for drum authoring (task 1.2 / 1.3)

Authoring the library surfaced three real primitive gaps. Each was closed by
improving a general-purpose primitive, not by adding a drum-specific module.

1. **Oscillator waveform selection.** The oscillator was saw-only. It now takes
   a `waveform` parameter (`saw` — the unchanged default — plus `sine`,
   `triangle`, `square`). `saw` preserves the historical rising-ramp behaviour so
   existing patches are byte-identical.
2. **Frequency-oriented oscillator tuning.** The oscillator now also takes a
   fixed `pitch` parameter: a ratio of the documented 220 Hz base
   (`OSCILLATOR_BASE_HZ`), e.g. `pitch: 2.45 ≈ 539 Hz`. This gives fixed-pitch
   voices (like the cowbell) a tuning path independent of note tracking, and the
   pitch-ratio mapping is now documented rather than implicit.
3. **Runtime-updatable decay.** The `decay` primitive baked `time_ms` into its
   state at construction, so decay knobs could not change at runtime. `time_ms`
   is now a live control input: a `decay.time_ms` target exposed through
   `preset_surface.parameters` updates the runtime decay length without
   rewriting or reparsing YAML. `gain.gain` and the `curve_mapper`
   scale/offset/amount/bias controls were likewise made settable-as-parameters so
   level trims and pitch shaping update live.

### Authoring constraint: keep voice gains ahead of the summing bus

`audio_mixer` is a **global** summing bus. Routing its output back into a
voice-scoped `gain` silently drops the audio (the per-voice meaning is
undefined). Author each oscillator/noise layer through its own voice-scoped
filter/gain chain and only sum at the final `audio_mixer`. The parallel-path
layout of `drum-808-cowbell.yaml` and `drum-808-snare.yaml` illustrates this.

## 3. Sampler fallback for 909 metallic voices (task 3.2)

Primitive synthesis of high-frequency metallic transients (hats, crash, ride) is
a known-hard problem, so those 909 voices are sampler-backed. This is the one
place the design permits sampler assets as the default.

The referenced assets in `examples/assets/drums/909/` are **self-authored
synthetic placeholders** generated by
`scripts/generate-909-placeholder-samples.py` (deterministic filtered noise
bursts). They exist only so the instruments load and render in tests. Production
users point the sampler asset path at their own licensed samples.

## 4. Reference-seeded parameter defaults and provenance (tasks 4.1, 4.2, 4.3)

Public documentation of 808/909-style instruments (service manuals, open
schematics, and freely inspectable open-source emulations) informs the initial
`preset_surface.parameters[*].default` values. These are treated as **tuning
hints, not ground truth**, and are converted into Dandrum's own parameter ranges
and units — never copied verbatim as code or assets.

Representative seed rationale (all values are starting points, refined offline):

- **Kick tune/decay/sweep.** 808 kicks favour a long (~650 ms) body decay with a
  deep, slow pitch sweep; 909 kicks are shorter (~260 ms) and punchier with a
  fast, deep sweep and a bright click. Seeded accordingly.
- **Snare tone vs snappy.** 808 snares balance a tuned ~180 Hz body tone against
  a highpassed noise "snap"; 909 snares are brighter and noise-dominated. The
  `tone_level`/`snappy` split encodes this.
- **Cowbell partials.** The 808 cowbell is fixed-pitch with two inharmonic square
  partials at roughly a 1.48 ratio (~540 Hz and ~800 Hz). Seeded as `pitch: 2.45`
  and `pitch: 3.63` (ratios of the 220 Hz base).
- **Clap.** Modelled as a bright noise "snap" over a slightly longer diffuse
  noise tail; the multi-burst structure of hardware claps is approximated by the
  two decay layers and refined offline.

### No proprietary content (task 4.3)

The repository contains **no** proprietary drum-machine samples, plugin source,
or preset banks. Reference values are re-derived into Dandrum units; the only
bundled audio assets are the self-authored placeholder noise bursts of §3.

## 5. Offline spectral/envelope tuning plan (task 5.2)

Seed values are tuned by ear only until an offline comparison workflow refines
them. That workflow runs **entirely outside the realtime audio callback** and
only ever changes public parameter values or authored YAML defaults — never
hidden graph structure.

Planned workflow:

1. **Render candidates.** For each drum instrument, render the voice offline
   (`DandrumEngine::render_patch_file_offline`) across a small grid of its public
   parameter values and a fixed trigger.
2. **Extract metrics.** Compare each candidate against one or more reference
   samples (supplied by the user, not bundled) using:
   - short-time spectral magnitude (reuse `src/spectral.rs` / `src/fft.rs`),
   - amplitude-envelope shape (attack, decay time, tail energy),
   - transient sharpness (onset slope),
   - decay-tail length to a threshold.
3. **Fit.** Search the public-parameter grid (or a local optimiser) for the
   candidate minimising a weighted metric distance.
4. **Propose or apply.** Emit the fitted `preset_surface` defaults for human
   review, or write them back into the authored YAML defaults.

Because the tool only reads rendered audio and writes public parameter values,
it cannot introduce hidden graph mutations that bypass `preset_surface.parameters`
or immutable instrument semantics.
